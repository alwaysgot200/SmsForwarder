# 修复无发件人短信转发及后续的 bug —— 方案文档

- 日期：2026-11-05
- 状态：已批准，实施中（批准决定见第九节）
- 范围：SmsForwarder topway 分支（相对上游 pppscn/SmsForwarder 的自有改动）
- 关联提交：7e00399f（智能短信双通道补漏）、ae40861f（短信接收空指针/类型转换加固）

---

## 一、背景

vivo/OPPO 等系统的"智能消息卡片识别"会把短信发件人号码替换为名称（如"丰巢"）或清空，且部分消息不触发 SMS_RECEIVED 广播、由系统直接写入短信库，导致漏转发。7e00399f 增加了"取号回退链 + 短信库监听补漏"解决漏转发，但实测暴露两个新 bug：

- 问题 A（严重）：App 首次安装后，只要打开"转发短信广播"开关，就把整个收件箱的历史短信全部处理并转发，形成"转发灾难"；只在首次出现，之后不再发生；卸载重装后必现。
- 问题 B：现在每收到一条短信会转发 2 次（间隔约 3 秒，内容完全相同）。

另有隐私疑问：无转发规则、无发送通道时，"全量转发"发到了哪里？是否存在未知服务器？

## 二、根因分析

### 2.1 问题 A：首装全量转发（水位线初始化时序 bug）

短信库监听（SmsDbObserver）用水位线（lastId）保证"只处理注册之后新入库的短信"，但初始化存在权限时序缺陷：

| 步骤 | 代码位置 | 实际行为 | 后果 |
|---|---|---|---|
| 1. App 启动注册监听 | App.kt 第 272 行 | 注册发生在 READ_SMS 运行时权限授予之前（首次安装必经） | 进入步骤 2 |
| 2. 初始化水位线 | SmsDbObserver.kt 第 45-49 行 | 调 queryMaxId() 取短信库最大 id，无权限时异常被吞、返回 0，且被写入为水位线 | 水位线 = 0 |
| 3. 打开"转发短信广播" | SmsDbObserver.kt 第 61 行 | 扫描入口只判断总开关，不看转发规则（与广播通道语义一致） | 进入步骤 4 |
| 4. 下一次短信库变更触发扫描 | SmsDbObserver.kt 第 89 行 | 查询条件 `_id > 0 且 type = 1`，即整个收件箱 | 历史短信全量进入转发流水线 |
| 5. 扫描结束推进水位线 | SmsDbObserver.kt 第 77 行 | 水位线推到当前最大 id | 一次性现象，之后不再出现 |

与观察现象完全吻合：首装必现（步骤 1-2 的时序固定）；只出现一次（步骤 5）；卸载重装后必现（权限收回回到步骤 1）。

补充澄清"根本不考虑转发规则"：扫描入口确实不看规则（只看总开关），但每条消息进入发送流程后一定经过规则匹配（SendWorker.kt 第 89-103 行，广播/短信库两通道同一路径，无旁路）——命中规则的真发送，未命中的只写入本地"转发日志"（SendWorker.kt 第 90-93 行）。

### 2.2 问题 B：每条短信转发 2 次（去重缺口）

同一条物理短信存在多个入口：Manifest 同时注册 SMS_RECEIVED、SMS_DELIVER、OppoSpeechAssist.SMS_RECEIVED 三个广播动作（AndroidManifest.xml 第 358-367 行，智能信息机型可能一条短信投递其中两个），加上新增的短信库监听入口。现有去重有两处缺口：

| 缺口 | 代码位置 | 说明 |
|---|---|---|
| 只做跨通道互斥，无同通道去重 | SmsUtils.kt 第 88-103 行 | 同通道到达两次（如两个广播动作）直接放行 |
| 指纹对内容逐字节取 md5 | SmsUtils.kt 第 95 行 | 广播体与短信库存储体若有空白等细微差异，指纹不一致，跨通道去重失效 |
| SendWorker 自带重复过滤默认关闭 | SettingUtils.kt 第 75 行 | duplicateMessagesLimits 默认 0，第二道防线不存在 |

两个副本被 WorkManager 顺序执行，间隔数秒，即图 1 中"6 秒前 / 9 秒前"两条相同记录。以前未出现是因为智能消息在广播入口被漏掉（原始 bug），修复后多入口同时产出副本，去重缺口才暴露。

### 2.3 隐私疑问澄清（结论：无未知服务器）

短信内容去向只有两个：

1. 命中规则后，经用户配置的发送通道外发（SendWorker.kt 第 97-103 行 → SendUtils）；
2. 写入手机本地数据库，即"转发日志"页面所显示的内容。

无规则、无通道时只入库不外发。截图中卡片上的"绿色图标 + 文字（80小ii）"是发送通道名称与发送状态（MsgPagingAdapter.kt 第 40-52 行），说明那批测试确实命中规则并真实发送到了该通道。上游自带联网仅有：友盟运营统计（隐私同意后才上报，不含短信内容）、XUpdate 版本检查（只发版本信息），均非本次改动引入。

## 三、行为语义定义（先定规则，再改代码）

| 场景 | 期望行为 |
|---|---|
| 首次安装后任意时点打开转发开关 | 只转发此后新收到的短信，历史短信一律不补发 |
| 转发开关关闭期间收到的短信 | 不补发（开关只影响此后新短信；两通道语义一致） |
| 同一条短信经多个入口到达 | 6 秒窗口内只转发 1 次（实时捕捉的短信前后几秒内到达的副本视为同一消息） |
| 不同号码恰好发出完全相同的文案 | 都转发，不误杀（见 4.2 的 from 规则） |
| 长短信 | 完整转发 1 次，不拆条、不重复 |

## 四、修复方案设计

### 4.1 问题 A：水位线只前瞻、永不回扫（SmsDbObserver.kt）

水位线改为"未初始化 / 已初始化"两态，任何情况下不允许把 0 写入水位线：

| 时机 | 行为 |
|---|---|
| 注册监听 | 只注册，不再初始化水位线（消除权限时序耦合） |
| 扫描触发且水位线未初始化 | 只前瞻不回扫：水位线推进到当前最大 id，吞掉历史存量；仅处理最近 60 秒内入库的行（即触发本次扫描的新短信，见下方说明） |
| 扫描触发且总开关关闭 | 水位线推进到当前最大 id 后结束（吞掉关闭期间的存量，不补发；未初始化时同样吞掉并完成初始化） |
| 扫描触发且水位线已初始化、开关开启 | 只处理 `_id > 水位线` 的新行，处理完推进水位线 |
| queryMaxId 失败（无权限等） | 保持现状（含未初始化），下次扫描重试；日志明确记录 |

扫描决策抽为纯函数 planSmsDbScan（返回水位线新值、查询范围、是否分发），配套单元测试。

实施中对初版方案的一处优化（结合实施代码更新方案）：初版"初始化即吞掉全部存量"会把触发首次扫描的新短信一并吞掉——若它是无广播的智能短信（本修复的核心场景）即漏转发。故初始化时增加"最近 60 秒内入库行"保护窗口：触发扫描的新短信 date ≈ 当前时间必然命中保护；卸载重装测试中的前一条测试短信通常已是数分钟前入库，不会被误补发。与"只转发此后新收到的短信、历史短信一律不补发"的语义一致。

效果：无论权限何时授予、开关何时打开，都只处理"初始化时刻之后新入库"的短信，从机制上杜绝历史回扫。

### 4.2 问题 B：统一消息指纹去重（SmsUtils.kt）

把现有"跨通道互斥"升级为"同通道 + 跨通道统一去重"，覆盖所有入口组合：

| 设计点 | 方案 |
|---|---|
| 指纹 | 归一化内容后取 md5：内容去除首尾空白并折叠连续空白，再结合消息类型（消除广播体/库存体细微空白差异导致的指纹不一致） |
| 丢弃条件 | 6 秒窗口内已有同指纹记录，且两者 from 相同、或任一 from 为空 → 丢弃后到者 |
| 不丢弃条件 | 同指纹但 from 明确不同 → 视为两个发件人恰好同文案，都转发（不误杀业务短信） |
| 存储 | 由"每条消息一个存储键"改为单键滚动记录（最近 50 条：指纹、from、时间、通道），随写入自动淘汰过期条目，避免长期使用后配置存储无限膨胀 |
| 日志 | 丢弃时输出"统一去重：已处理相同消息，跳过"，含两个通道名，便于现场定位 |

设计取舍说明：from 以"相同或空"为匹配条件，是因为智能消息场景下广播回退链解析出的号码与短信库 address 可能一个有值一个为空，同一物理消息不能因此漏去重；而两个明确不同号码的同文案短信全部保留，优先保证"不漏"。

### 4.3 第二道防线：默认启用重复过滤（SettingUtils.kt）

duplicateMessagesLimits 默认值由 0（关闭）调整为 6（秒），作为统一去重之后的兜底防线，键含发件人+内容，只拦截 6 秒内的完全重复，不影响正常短信。该值仍保留为设置项，用户可按需调整。

### 4.4 小硬化：消除 SmsReceiver 实例字段隐患（SmsReceiver.kt）

SmsReceiver 中 from、msg 目前是实例字段、靠累加拼接分段内容；静态注册的接收器每次广播新建实例故当前无恙，但一旦改为动态注册即成串号隐患。将两字段收敛为 onReceive 内的局部变量，消除这一脆弱点（纯结构调整，行为不变）。

## 六、边界与风险

| 边界/风险 | 评估与对策 |
|---|---|
| 长短信分段存储 date 不完全一致时可能拆条 | 保持现有"同发件人 + 完全相同 date 归并"策略；拆条属罕见 OEM 行为，日志可查，本次不扩范围 |
| 同指纹不同 from 的判定依赖 from 解析质量 | 解析失败一侧按"空"处理并参与去重，宁可少去重一条也不误杀 |
| 滚动记录 50 条的窗口容量 | 6 秒窗口内到达 50 条以上短信才可能溢出，溢出表现为重复转发而非漏转发，风险可接受 |
| 初始化保护窗口依赖短信库 date（短信中心时间戳） | 本机时间与短信中心偏差超过 60 秒的极罕见场景下，触发首次扫描的那条短信可能被吞；只影响首次扫描这一条，其后水位线已初始化不再受影响。权衡：避免卸载重装测试把数分钟前的旧短信误补发 |
| 开关关闭期间存量不补发 | 属明确产品语义（见三），如需改为补发可后续做成配置项 |
| 与上游合并冲突 | 改动集中在 4 个自有文件，SmsUtils/SmsDbObserver 为本分支新增文件，冲突面小 |

## 九、批准决定记录（2026-11-05 用户确认）

1. "开关关闭期间收到的短信不补发"——认可。补充语义：短信按时间实时捕捉，只有监控条件满足时才转发；最近捕捉到的短信，转发规则满足即转发。
2. "同文案不同发件人都转发（宁重不漏）"——认可。
3. 重复过滤窗口——否决 60 秒，定为 **6 秒**：实时捕捉的短信副本只会在前后几秒内到达，6 秒足够；统一去重窗口与 duplicateMessagesLimits 默认值均按 6 秒执行。
4. 本文档与修复代码提交进 git，文档放在 docs/ 目录下。

## 十、生产级质量审查与二次加固（2026-11-05，发布 v3.5.3 前）

修复代码落地后做全量质量审查（需求完成度、业务闭环、性能、边界异常、重复造轮子、解耦可维护性）。核心逻辑（水位线状态机、统一指纹去重）业务闭环完整、边界与异常处理充分、单测覆盖到位，无阻断问题。但发现一处被 4.3 默认值改动"激活"的存储膨胀问题，并顺带消除重复实现：

| # | 维度 | 问题 | 处置 |
|---|---|---|---|
| 1 | 性能/存储瓶颈 | 4.3 将 duplicateMessagesLimits 默认 0→6 后，SendWorker / SmsCommandUtils 中"每条消息/指令一个 md5 存储键"的旧去重开始对每条消息永久写入 `.history`，随消息量无限膨胀（SharedPreferences 全量载入内存，长期使用拖慢启动） | 新增 `DuplicateFilter`：单键滚动记录（最近 200 条），存储有界 |
| 2 | 重复造轮子 | SendWorker 与 SmsCommandUtils 的去重逻辑100% 相同（md5 键 + 时间戳 + 窗口比较），散落两处 | 收敛为 `DuplicateFilter.isDuplicate`，单一实现两处复用 |
| 3 | 垃圾数据 | 旧版遗留 `xch_*` 跨通道键（≤3.5.2）与历史 md5 键仍堆积 `.history`，无清理机制 | `DuplicateFilter.migrateLegacy()` 升级后首次启动一次性清除（幂等） |
| 4 | 可维护性 | 去重判定逻辑分散、无统一封装 | 去重判定抽为纯函数 `isDuplicateWindow`，配套单测 |

涉及文件（本次）：新增 `utils/DuplicateFilter.kt`（含纯函数去重判定 + 遗留键清理）、`utils/HistoryUtils.kt`（新增批量按键删除 `removeKeysIf`）、`workers/SendWorker.kt` 与 `utils/SmsCommandUtils.kt`（改用 DuplicateFilter，移除重复实现）、`App.kt`（启动接入 migrateLegacy）、新增 `utils/DuplicateFilterTest.kt`。

去重语义与窗口保持不变（统一去重 6 秒、duplicateMessagesLimits 默认 6 秒、系统指令多加 10 秒），仅改造存储与封装，不改变业务行为。验收：V1–V7 不受影响，16 项单测全过（新增 4 项）、assembleRelease 编译通过。
